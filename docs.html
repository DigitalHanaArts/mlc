01Installation

Python 3.10+, a C++17 compiler, CMake ≥ 3.20, OpenSSL, SQLite3, and Boost headers. On Linux and macOS: 

git clone https://github.com/digitalhanaarts/MLabChain
cd MLabChain
./build.sh
python -m pip install -e .
python mlabchain.py demo

On Windows, in PowerShell:

git clone https://github.com/digitalhanaarts/MLabChain
cd MLabChain
./build.ps1
python -m pip install -e .
python mlabchain.py demo

03Wire protocol

The P2P protocol is line-delimited over TCP. Each message is a single UTF-8 line terminated by \n. The first token before | identifies the message type.

MessageDirectionMeaning
PING→Liveness probe.
PONG←Liveness response.
STATUS→Request node status.
STATUS|H|TIP|WORK←Height, tip hash, cumulative work.
GETCHAIN→Request the full chain.
BLOCK|<wire>←A single block, hex-encoded fields separated by |.
END←End of a GETCHAIN response.
TX|<wire>bothRelay a signed transaction.
OK←Message accepted.
ERROR|msg←Message rejected.

04Challenge manifest schema

The manifest is a JSON document. Its canonical form — sorted keys, no whitespace, UTF-8 — is hashed to produce manifest_sha256. Any deviation from canonical form will change the hash. 

{
  "challenge_id": "MLC-LINEAR-001",
  "description": "Deterministic synthetic linear regression",
  "dataset_kind": "synthetic_linear",
  "dataset_sha256": "…",
  "n_samples": 1200,
  "n_features": 4,
  "generator_seed": 42,
  "generator_noise": 0.1,
  "split_rule": "first_fraction",
  "train_fraction": 0.8,
  "metric": "NMSE",
  "baseline_kind": "mean_predictor",
  "baseline_nmse": 1.0,
  "baseline_model_sha256": null,
  "max_epochs": 100,
  "verifier": "MLabChain-linear-v4",
  "schema_version": 4,
  "manifest_sha256": "…"
}

06Error codes

Errors are returned as ERROR|message on the wire, or printed as ERROR=message by the core CLI. The most common ones:

MessageCause
invalid sender addressAddress fails the checksum or the prefix check.
invalid Ed25519 signatureSignature does not verify against the public key and message.
invalid account nonceNonce is not exactly account_nonce + pending_count + 1.
insufficient balanceSender balance is less than amount + fee, accounting for pending reservations.
fee below minimumFee is below the current min_fee.
challenge is not registeredThe referenced challenge does not exist on-chain.
challenge is not activeSubmission is before activation or after expiry.
ML result does not improve challenge bestThe new quality is not strictly greater than the current best.
ML reward mismatchThe claimed reward does not match the formula applied to the marginal delta.
duplicate ML work claimThe (challenge, dataset, model) tuple was already paid.
maximum supply exceededIssuance would push supply past 100,000,000 MERA.
challenge reward budget exceededIssuance would exceed the challenge's remaining budget.
unsupported database schemaThe SQLite file was created by an incompatible protocol version.

07Migration from v0.2

v0.3 refuses to open a v0.2 database. This is intentional: the consensus rules changed, and silently replaying old history under new rules would be less safe than an explicit boundary.

To migrate: 

python tools/migrate_v2.py \
  --input ./old/mera_data/mera.sqlite \
  --output ./migration/v2_snapshot.json

The output is a JSON snapshot containing every account's balance and nonce, the old genesis hash, the old tip, and a SHA-256 over the whole snapshot. A production migration is expected to define a new genesis that commits to this snapshot before importing balances.

Why an explicit boundary

v0.2 and v0.3 use different reward formulas, different address formats, and different state layouts. A mechanical rewrite of a v0.2 database into a v0.3 one would silently reinterpret history. An explicit migration ceremony — with a signed snapshot that both sides agree on — is slower but auditable.
